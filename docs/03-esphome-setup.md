# 3 — KinCony KC868-A4 / ESPHome

## First-time bench preparation

1. Confirm the unit is a **KC868-A4**. Its **digital input terminal** is labeled `D1 D2 D3 D4 GND`. Relay bank contains four groups of `NO/COM/NC` (verify markings on your hardware).
2. Use a **regulated 12 V DC** supply of adequate capacity; many barrel adapters are center-positive, but verify **both actual wires with a meter** before connecting to the board's `12V`/`GND` input. The power supply's center-positive symbol does *not* guarantee the adapter lead colors.
3. Keep **all LiftMaster wiring disconnected** during bench work.
4. Configure/fl​ash ESPHome using the [KinCony project](https://hzkincony.github.io/kc868-a4/) or your ESPHome Device Builder and connect to your Wi-Fi and Home Assistant.
5. The manufacturer's package is [`hzkincony/kc868-a4`](https://github.com/hzkincony/kc868-a4/blob/main/kc868-a4.yaml). It exposes raw GPIO relays/inputs; a dedicated gate configuration is preferable for **momentary** commands. **Do not combine the original package and a complete replacement configuration**: both would attempt to define the same GPIOs.

## GPIO mapping (from KinCony's actual package)

| Function | GPIO |
|---|---|
| Relay 1 | GPIO2 |
| Relay 2 | GPIO15 |
| Relay 3 | GPIO5 |
| Relay 4 | GPIO4 |
| Digital Input 1 | GPIO36 (inverted) |
| Digital Input 2 | GPIO39 (inverted) |
| Digital Input 3 | GPIO27 (inverted) |
| Digital Input 4 | GPIO14 (inverted) |

> Some third-party device catalogues have incorrectly copied relay GPIOs as the digital input pins. **Use KinCony's own YAML and board labeling.**

## Example configuration

See [`esphome/gate-controller.example.yaml`](../esphome/gate-controller.example.yaml). It contains:

- GPIO2 and GPIO15 as **internal** momentary relays (500 ms pulse, mutually interlocked in software).
- GPIO5 as an **internal** maintained Party Mode relay, with an exposed **template switch** that only enables when both limit inputs say fully open; turning off is always allowed.
- GPIO4 reserved/off.
- All four input sensors, including validated D1/D2 signals and spares D3/D4.
- `Gate Open` and `Gate Close` button entities with limit-state guards (a button is still not a safety control).
- A `Gate Position` text sensor reporting `Closed`, `Between Limits`, `Open`, or `Invalid State`.
- Relay `restore_mode: ALWAYS_OFF` to avoid a restored latched Party Mode after reboot.

**If the unit is already running a working configuration**, back it up before upgrading. The example uses a different logical structure (a template Party Mode switch instead of exposing raw Relay 3) and **may change your Home Assistant entity IDs**. Confirm which entities are created and edit the dashboard accordingly.

Fill `secrets.yaml` locally using [`secrets.example.yaml`](../esphome/secrets.example.yaml), substituting unique Wi-Fi credentials and the API key generated by ESPHome. **Never commit `secrets.yaml`.**

## Bench tests

- Press Open once: Relay 1 clicks briefly, then returns OFF.
- Press Close once: Relay 2 clicks briefly, then returns OFF.
- Turn Party Mode ON with *simulated open-limit input asserted*: Relay 3 stays energized until switched OFF.
- Party Mode **must not enable** when the open-limit inputs are not valid (if using the hardened template-switch example).
- Temporarily close **D1 to input GND**: Input 1 LED turns on, HA `Gate Input 1` becomes ON. Repeat with D2, D3, D4 one at a time.
- Power-cycle with Party Mode energized, with **no gate attached**: verify all relays are OFF after restart and observe for any unexpected brief activation during boot.

**Caveat:** `restore_mode: ALWAYS_OFF` and ESPHome software interlocks are *not* electrical fail-safe devices. GPIOs can briefly change during boot *before* firmware configures them. Hardware and gate-system safety protections remain mandatory.
